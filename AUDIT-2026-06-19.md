# DreamSeed Audit — 2026-06-19

> Полный аудит безопасности, конфигурации и IaC-кода.
> Все проблемы обнаружены в ходе ревью codebase.

## 1. Критические (Critical)

### 1.1 Terraform check-блоки: неверное сравнение workspace

| |
|---|---|
| **Файл** | `terraform/aws/main.tf:137-142` + `terraform/hetzner/main.tf:124-128` |
| **Проблема** | Check-блоки используют `terraform.workspace`, который в Terraform Cloud возвращает полное имя (`dreamseed-prod`), но сравнение идёт с короткими именами (`prod`). |
| **Почему плохо** | Дрифт-детекция всегда выдаёт false-positive — проверка никогда не проходит в TFC. Инфраструктурные изменения остаются незамеченными среди шума ложных срабатываний. |
| **Исправление** | Заменить `terraform.workspace` на `var.environment` во всех check-блоках. |

### 1.2 Валидация .env: multi-line injection

| |
|---|---|
| **Файл** | `lib/env.sh:16-19` |
| **Проблема** | Валидация .env проверяет наличие инъекционных символов (`;`, `$(`, `` ` ``) только на первой строке. Multi-line quoted value типа `VAR="safe\n$(rm -rf /)"` проходит проверку. |
| **Почему плохо** | `source` выполнит инъекцию. Злоумышленник, получивший доступ к `.env`, может выполнить произвольный код во время деплоя. |
| **Исправление** | Добавить проверку continuation lines (строк, оканчивающихся на `\`) перед skip-логикой. |

## 2. Высокие (High)

### 2.1 SSH порт открыт на весь мир

| |
|---|---|
| **Файл** | `terraform/aws/main.tf:36-43` |
| **Проблема** | SSH (порт 22) разрешён с `0.0.0.0/0` и `::/0`. Директива `#tfsec:ignore` подавляет предупреждения сканеров. |
| **Почему плохо** | Сервер доступен для брутфорса SSH со всего интернета. Без дополнительной защиты (fail2ban, key-only) — высокий риск компрометации. |
| **Исправление** | Ограничить CIDR блоком IP-адреса деплоера или использовать bastion host. |

### 2.2 Security group: диапазон 80-443 вместо двух портов

| |
|---|---|
| **Файл** | `terraform/aws/main.tf:63-69` + `terraform/hetzner/main.tf:48-52` |
| **Проблема** | `from_port=80, to_port=443` открывает 363 порта (80–443), а не только 80 и 443. |
| **Почему плохо** | Открыты все порты диапазона (81, 82, …, 442), включая потенциально опасные (например, 443 — HTTPS, но и 8080, 8443 и т.д.). Поверхность атаки излишне широка. |
| **Исправление** | Создать две отдельные записи: `from_port=80, to_port=80` и `from_port=443, to_port=443`. |

### 2.3 AMI `most_recent = true`

| |
|---|---|
| **Файл** | `terraform/aws/main.tf:6-20` |
| **Проблема** | `most_recent = true` для AMI — каждый `terraform apply` может получить другой образ ОС. |
| **Почему плохо** | Воспроизводимость отсутствует. Разные версии пакетов, разное поведение cloud-init. Dev-стенд может отличаться от prod. |
| **Исправление** | Зафиксировать конкретный AMI ID или использовать SSM Parameter Store (`/aws/service/canonical/ubuntu/server/.../stable/current/amd64/hvm/ebs-gp2/ami-id`). |

### 2.4 Elastic IP не управляется Terraform

| |
|---|---|
| **Файл** | `terraform/aws/main.tf` |
| **Проблема** | Elastic IP управляется через `deploy.sh` (внешний скрипт), а не Terraform. `terraform destroy` не отвяжет EIP. |
| **Почему плохо** | При разрушении инфраструктуры EIP остаётся закреплённым и продолжает тарифицироваться (~$3.6/мес). Ручная очистка забывается. |
| **Исправление** | Добавить ресурс `aws_eip_association` в `main.tf`. |

### 2.5 Hetzner: `ignore_changes` на ssh_keys и user_data

| |
|---|---|
| **Файл** | `terraform/hetzner/main.tf:115-121` |
| **Проблема** | `ignore_changes = [ssh_keys, user_data]` — если ключ удалён из Hetzner-аккаунта, Terraform не восстановит его. |
| **Почему плохо** | Полная блокировка SSH-доступа к серверу. Восстановление — только через Hetzner Rescue Mode. |
| **Исправление** | Убрать `ignore_changes` или добавить внешнюю проверку (например, `hcloud_ssh_key` data source). |

### 2.6 PHP-FPM: жёсткие pm-параметры при динамическом max_children

| |
|---|---|
| **Файл** | `ansible-roles/php/templates/www.conf.j2:11-13` |
| **Проблема** | `pm.start_servers=5`, `pm.max_spare_servers=10` жёстко забиты. `pm.max_children` вычисляется динамически из RAM (`{{ (ansible_facts['memtotal_mb'] / 40) }}`). На малом сервере (2GB) `max_children` будет ~50, что допустимо. Но если `max_children` упадёт до 2 (крайне малый сервер), `start_servers=5` превысит его, и PHP-FPM упадёт. |
| **Почему плохо** | PHP-FPM не стартует на малом сервере. Деплой проходит успешно, но сайт не работает. |
| **Исправление** | Обернуть в capped Jinja-выражения: `pm.start_servers={{ [2, (max_children * 0.1)] | min }}`. |

### 2.7 Lock-файлы в `/tmp`

| |
|---|---|
| **Файл** | `scripts/smart_backup.sh:39-40` + `scripts/RESTORE_ALL.sh:5-9` |
| **Проблема** | Lock-файлы создаются в `/tmp` — world-writable каталог. |
| **Почему плохо** | Symlink-атака: злоумышленник может создать симлинк с именем lock-файла на любой файл системы (например, `/etc/passwd`). Скрипт с правами root перезапишет его содержимым lock-файла. |
| **Исправление** | Перенести в `~/.locks/` или использовать `flock` с O_CREAT. |

### 2.8 `grep -qP` — GNU extension

| |
|---|---|
| **Файл** | `scripts/setup_betteruptime.sh:62` |
| **Проблема** | `grep -qP` использует Perl-совместимые regex (GNU extension). На macOS (BSD grep) флаг `-P` отсутствует. |
| **Почему плохо** | Скрипт дублирует записи в `.env` при каждом запуске на macOS. Под Linux работает, но портабельность нарушена. |
| **Исправление** | Заменить на `grep -qE` (BRE/ERE, переносимо). |

### 2.9 SSL: отсутствует certbot webroot fallback

| |
|---|---|
| **Файл** | `ansible-roles/ssl/tasks/main.yml:56-92` |
| **Проблема** | В документации (CLAUDE.md, README) обещан certbot webroot fallback при отсутствии Cloudflare токена. В коде его нет — без CF токена сразу self-signed. |
| **Почему плохо** | Продуктовый сервер может получить самоподписанный сертификат без единого уведомления. Посетители увидят ошибку SSL. Обещание в документации не соответствует реальности. |
| **Исправление** | Реализовать webroot-проверку: DNS → сервер → certbot webroot. |

### 2.10 `ansible-playbook` в check mode без переменной $ANSIBLE_PLAYBOOK

| |
|---|---|
| **Файл** | `deploy.sh:229` |
| **Проблема** | В check mode `ansible-playbook` вызывается голым бинарём, а не через `$ANSIBLE_PLAYBOOK` (как остальные вызовы). |
| **Почему плохо** | Если пользователь переопределил `ANSIBLE_PLAYBOOK` (например, через docker или venv), check mode использует другую версию Ansible — неконсистентное поведение. |
| **Исправление** | Использовать `"${ANSIBLE_PLAYBOOK:-ansible-playbook}"`. |

## 3. Средние (Medium)

### 3.1 Ansible remote_tmp в /tmp

| |
|---|---|
| **Файл** | `ansible/ansible.cfg:5` |
| **Проблема** | `remote_tmp = /tmp`. Ansible копирует скрипты с секретами в мир-читаемый каталог на целевой сервер. |
| **Почему плохо** | Любой пользователь сервера может прочитать скрипты Ansible, содержащие пароли и токены. |
| **Исправление** | `remote_tmp = ~/.ansible/tmp` |

### 3.2 a2enmod через command модуль

| |
|---|---|
| **Файл** | `ansible-roles/apache_http/tasks/main.yml:4` |
| **Проблема** | `a2enmod` вызывается через `command` модуль, а не через `apache2_module`. |
| **Почему плохо** | Ручной модуль Ansible идемпотентен и проверяет, включён ли модуль. `command` бежит каждый раз. Нарушение best practices. |
| **Исправление** | Использовать `apache2_module` модуль. |

### 3.3 fail2ban-grafana.filter: экранирование %%

| |
|---|---|
| **Файл** | `ansible-roles/security/files/fail2ban-grafana.filter:11` |
| **Проблема** | `datepattern = %%Y-%%m-%%d %%H:%%M:%%S`. Файл лежит в `files/` (не template), `%%` не обрабатывается Jinja2, но fail2ban ожидает одиночный `%`. |
| **Почему плохо** | Фильтр мёртвый — fail2ban не парсит логи Grafana. Брутфорс Grafana не блокируется. |
| **Исправление** | Заменить на одиночный `%` или перенести файл в `templates/` и использовать замену Jinja. |

### 3.4 SSH hardening config с mode 0644

| |
|---|---|
| **Файл** | `ansible-roles/security/tasks/main.yml:7` |
| **Проблема** | SSH config `99-hardening.conf` копируется с `mode: 0644` (world-readable). |
| **Почему плохо** | SSH конфигурация (включая запрещённые методы auth) доступна любому пользователю. Информация для атаки. |
| **Исправление** | Установить `mode: 0640` (owner + group read). |

### 3.5 DB_PREFIX не синхронизирован с MODX_TABLE_PREFIX

| |
|---|---|
| **Файл** | `ansible-roles/backup/templates/server.env.j2:18` |
| **Проблема** | `DB_PREFIX` default: `db_` + `{{ db_name }}` + `_`, но `MODX_TABLE_PREFIX` = `modx_`. При отсутствии env var бэкап не захватит таблицы MODX. |
| **Почему плохо** | Бесполезный бэкап, который не обнаружит проблему до restore. |
| **Исправление** | Синхронизировать префиксы: `DB_PREFIX` default должен совпадать с `MODX_TABLE_PREFIX`. |

### 3.6 Health check отключает проверку SSL

| |
|---|---|
| **Файл** | `ansible-roles/monitoring/templates/check_site.sh.j2:8` |
| **Проблема** | `curl -sfk` отключает проверку SSL-сертификата. |
| **Почему плохо** | Health check не заметит проблем с сертификатом (просрочен, невалиден, самоподписан). Ложное чувство безопасности. |
| **Исправление** | Использовать `http://127.0.0.1` (локальный health check) или убрать `-k` и проверять HTTPS через валидный домен. |

### 3.7 `compgen -v` не работает на macOS

| |
|---|---|
| **Файл** | `deploy.sh:449` |
| **Проблема** | `compgen -v` — bash 4.2+ builtin. macOS использует bash 3.2. |
| **Почему плохо** | `deploy.sh` падает на macOS при попытке экспорта переменных. Разработчики на macOS не могут запустить деплой локально. |
| **Исправление** | `for var in $(env \| grep '^PROD_\|^DEV_\|^HCLOUD_' \| cut -d= -f1)` вместо `compgen -v`. |

### 3.8 deploy_history.log без chmod 600

| |
|---|---|
| **Файл** | `deploy.sh:40` |
| **Проблема** | `deploy_history.log` создаётся с правами по умолчанию, без `chmod 600` (в отличие от `DEPLOY_VARS_TMP`). |
| **Почему плохо** | История содержит пути к логам, время деплоя, имена воркспейсов. Не критические секреты, но информационный лик. |
| **Исправление** | Добавить `chmod 600 "$LOG_FILE"` после создания. |

### 3.9 Race condition при создании temp-файла

| |
|---|---|
| **Файл** | `lib/env.sh:43` |
| **Проблема** | `mktemp` + отдельный `chmod 600` — race window между созданием и установкой прав. |
| **Почему плохо** | В момент между `mktemp` и `chmod` файл доступен для чтения другим процессам. |
| **Исправление** | Использовать `umask 077` перед `mktemp` или `mktemp -p /tmp -t` с корректной маской. |

### 3.10 Публичный SSH-ключ в .env.example

| |
|---|---|
| **Файл** | `.env.example:56` |
| **Проблема** | Реальный SSH публичный ключ Vitali находится в публичном репозитории. |
| **Почему плохо** | Публичный ключ — не секрет сам по себе, но засоряет диффы и позволяет связать аккаунты. Утечка приватного ключа делает сервер уязвимым. |
| **Исправление** | Заменить на placeholder `ssh-ed25519 AAAAC3... user@host`. |

### 3.11 Telegram MarkdownV2 без экранирования

| |
|---|---|
| **Файл** | `.github/workflows/deploy.yml:247` |
| **Проблема** | Telegram MarkdownV2 требует экранирования спецсимволов (`_`, `*`, `[`, `` ` ``, etc.). Никакого экранирования нет. |
| **Почему плохо** | Если в переменных окружения или выводе команд есть спецсимволы, уведомления в Telegram падают с ошибкой. Мониторинг деплоев не работает. |
| **Исправление** | Обернуть переменные в backtick или использовать функцию `escapeMarkdown`. |

### 3.12 `while fuser` без таймаута

| |
|---|---|
| **Файл** | `.github/workflows/test-restore.yml:369` |
| **Проблема** | `while fuser` ожидает освобождения файла без таймаута. |
| **Почему плохо** | Если процесс завис, джоба в GitHub Actions будет висеть 50 минут до дефолтного таймаута. Пустая трата runner-минут. |
| **Исправление** | Добавить таймаут: `timeout 120 bash -c 'while fuser ...'` |

### 3.13 cloud-init: нет apt-get update перед upgrade

| |
|---|---|
| **Файл** | `terraform/hetzner/cloud-init.tftpl:18` |
| **Проблема** | `apt-get upgrade -y` выполняется без предварительного `apt-get update`. |
| **Почему плохо** | На свежем образе с устаревшим кешем `apt-get upgrade` может пропустить обновления или упасть. |
| **Исправление** | Добавить `apt-get update -qq` перед `apt-get upgrade`. |

### 3.14 Ansible коллекции без точной версии

| |
|---|---|
| **Файл** | `ansible/requirements.yml` |
| **Проблема** | Коллекции указаны с `>=5.0.0` — без фиксации минорной версии. |
| **Почему плохо** | Мажорный апгрейд коллекции может сломать несовместимые модули. Разное поведение на разных машинах разработчиков. |
| **Исправление** | Зафиксировать точную версию: `5.0.0` или `>=5.0.0,<6.0.0`. |

### 3.15 MariaDB restart без проверки готовности

| |
|---|---|
| **Файл** | `ansible-roles/mariadb/tasks/main.yml:49` |
| **Проблема** | `flush_handlers` рестартует MariaDB, но следующая задача выполняется немедленно, без проверки готовности базы. |
| **Почему плохо** | Если MariaDB не успела перезапуститься, следующая задача (создание пользователя, настройка) упадёт. Деплой останавливается. |
| **Исправление** | Добавить `wait_for: port=3306 state=drained` или Ansible `mysql_info` модуль после restart. |

### 3.16 ShellCheck только severity: error в CI

| |
|---|---|
| **Файл** | `.github/workflows/ci.yml:31` |
| **Проблема** | ShellCheck запущен только на `severity: error`, игнорируя warning/info. |
| **Почему плохо** | Множество серьёзных проблем (неиспользуемые переменные, неправильные подстановки, потенциальные баги) классифицируются как warning. CI их пропускает. |
| **Исправление** | Использовать `severity: style` или `warning` (как минимум), или запускать без флага severity чтобы поймать все уровни. |
